PART 0 — BEFORE YOU HIT RECORD (do this first, in this order)
===============================================================================

A. Environment prep
   1. Close Slack/Discord/email — kill anything that can pop a notification.
   2. Set terminal font size to 16–18pt so text is readable on a recording.
   3. Set browser zoom to 100–110%, close all tabs except the dashboard.
   4. Turn off OS "do not disturb" toggle ON (ironic but correct — turn it ON
      so notifications don't interrupt).
   5. Have THREE terminal tabs/panes ready, each pre-loaded with the venv
      activated and the right working directory, so you never fumble typing
      "cd" or "source venv/bin/activate" on camera:
        Tab 1 — QEMU BMC simulator
        Tab 2 — FastAPI backend (main.py)
        Tab 3 — Streamlit dashboard (app.py)

B. Start services BEFORE recording, verify they work, THEN stop them and
   restart fresh on camera (so the audience sees the real boot sequence,
   but you already know it works and won't hit a surprise error live).

   Terminal 1 (QEMU):
     qemu-system-arm \
       -machine romulus-bmc \
       -m 512 \
       -drive file=tmp/deploy/images/romulus/obmc-phosphor-image-romulus.static.mtd,if=mtd,format=raw \
       -serial mon:stdio -serial null \
       -netdev user,id=net0,hostfwd=tcp::2443-:443 \
       -net nic,netdev=net0
     (wait ~60-90s for OpenBMC Linux to fully boot before touching the dashboard)

   Terminal 2 (backend):
     source venv/bin/activate
     python main.py
     # confirm you see: "Uvicorn running on http://0.0.0.0:8000"
     # sanity check in a spare terminal: curl -s http://localhost:8000/health

   Terminal 3 (dashboard):
     source venv/bin/activate
     streamlit run app.py
     # opens http://localhost:8501

C. Rehearse the click-path ONCE off-camera end to end:
     Diagnosis tab → pick "CPU Overheat" → Run Diagnosis → Auto-Remediate
     → Operations Hub tab → approve any pending action
     → Audit & Timeline tab → expand an incident
   This avoids dead air / hunting for buttons while recording.

D. Recording tool settings
   - OBS Studio (or ScreenStudio/Camtasia): 1920x1080, 30fps minimum, 60fps
     if you can afford the file size.
   - Record system audio OFF, mic ON, mic gain checked with a 5-second test
     clip played back before the real take.
   - Record webcam in a corner (optional) for the intro/outro talking-head
     bits; can be OFF during the pure demo/screen sections.
   - Do a 10-second test recording and check for audio sync / screen tearing
     before the real take.

[1:00 – 2:00] THE PROBLEM
--------------------------------------------------------------------
SHOW: Slide/title card with the bullet points below, OR just talking head.

SAY:
  "Here's the problem this solves. Server hardware failures cost
   enterprises an estimated $5,600 per minute of downtime. Traditional
   BMCs — OpenBMC, Dell iDRAC, AMI MegaRAC — give you raw sensor data, but
   zero intelligence. A human has to look at a temperature spike, a fan
   anomaly, a DIMM error, correlate them, figure out the root cause, and
   manually run the fix. Under pressure. At 3 AM.
   And the existing AIOps tools — Datadog, Dynatrace, New Relic — don't
   help here because they're cloud-first, they need OS-level agents, and
   none of them can act autonomously on hardware. They just alert you and
   leave the fixing to a human.
   AI OpsBMC closes that entire loop."

--------------------------------------------------------------------
[2:00 – 3:30] ARCHITECTURE OVERVIEW
--------------------------------------------------------------------
SHOW: Open README.md in the editor (or a rendered GitHub view) and scroll
      to the architecture ASCII diagram / the "Intelligence Pipeline"
      section. Alternatively, screen-share a whiteboard/diagram tool if
      you prefer drawing it live.

SAY:
  "The whole system covers one operational loop:
   Collect → Detect → Diagnose → Predict → Recommend → Approve → Execute
   → Audit.

   It's four independent microservices. The Collector polls the BMC over
   Redfish — the standard REST API for server management — and writes
   telemetry to a database. The Analytics service runs an Isolation
   Forest model for unsupervised anomaly detection — no labelled failure
   data required — plus a Random Forest predictor that forecasts failure
   probability 1, 5, and 15 minutes out.

   When something's flagged, the Agent service kicks in: a
   Retrieval-Augmented Generation engine — ChromaDB plus an
   all-MiniLM-L6-v2 embedding model — pulls in grounded domain knowledge
   about that specific fault type, feeds it to an LLM, and produces a root
   cause and a recommendation instead of a hallucinated guess.

   Then — and this is the part most AIOps tools don't do — a Policy
   Engine decides if that recommended action is safe to run
   automatically, or if it needs a human to approve it first. Either way,
   an Execution Engine runs it, a Rollback Manager watches system health
   afterward and auto-undoes the action if things got worse, and an Audit
   Logger records every single step, immutably."
